\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}

Chapter~2 closed on a sharpened question rather than an answer. Its composability analysis (\S\ref{sec:ch2-tension}) showed that Data Vault~2.0 and the Lakehouse do combine in current practice, but that the combination rests on an interface neither paradigm specifies: the modeling discipline assumes relational lineage and hash-keyed history, while the analytics stack assumes file access and schema-on-read. The chapter also produced the instrument needed to judge any proposed resolution --- the six-criteria evaluation grid (\S\ref{sec:ch2-criteria}). This chapter uses both outputs: it builds an architecture that names and governs that interface, then evaluates it with the grid.

This is the construct chapter, and it carries C3. A theoretical thesis is most exposed here, because a jury can attack a proposed architecture on two fronts. The first is specification: a block diagram with boxes and arrows but no component definitions and no stated contract is a picture, not an artifact. The second is evaluation: a comparison table with scores but no stated method reads as opinion, not assessment. This chapter is organized to close both fronts deliberately.

It closes the first front by presenting the framework as a formal artifact. Section~\ref{sec:ch3-requirements} derives the requirements from RQ1--RQ3 and the dual-scalability dimensions of \S\ref{sec:ch1-scalability}, so that every design choice traces to a stated need. Section~\ref{sec:ch3-framework} then specifies a layered reference model with named components and their responsibilities, an explicit integration contract between the agile modeling layer and the native analytics layer (\S\ref{subsec:ch3-contract}), and a set of numbered design invariants (\S\ref{subsec:ch3-invariants}) that can be probed one by one. The contract is the centerpiece: it states what the modeling layer guarantees to the analytics layer, and it scopes explicitly what it does not solve.

It closes the second front by stating the evaluation method before applying it. Section~\ref{sec:ch3-methodology} defines the assessment as conceptual and criteria-based, explicitly non-empirical, with a scoring rubric and an evidence rule that admits no bare scores. Section~\ref{sec:ch3-comparison} then applies that method across Kimball, Inmon, Data Vault~2.0, and the proposed framework, conceding where the framework inherits Data Vault~2.0's complexity cost rather than claiming it wins everywhere. Section~\ref{sec:ch3-discussion} examines the trade-offs, the conditions under which the architecture earns its complexity, and the limits of a validation that remains conceptual.

\subsection{Layered Reference Model}
\label{subsec:ch3-layers}

The framework is organized as four stacked functional layers resting on a shared storage
substrate and wrapped by one cross-cutting governance plane. The ordering follows the data
path: heterogeneous sources are captured at the bottom, integrated and historized in the
middle, and consumed at the top by two parallel paths --- business intelligence and native
analytics. The single design decision that distinguishes this arrangement from a
conventional warehouse is the placement of the analytics layer: it reads from the agile
modeling layer directly, not from the serving marts downstream of it. Figure~\ref{fig:ch3-architecture}
shows the model.

The arrangement answers the two scalability axes with distinct layers and couples them
through one substrate. Layer~2 carries structural scalability (Data Vault~2.0 mechanics);
layer~4 carries analytical scalability (native model integration); the open table format
lets both read the same physical data without a separate copy, and the governance plane
makes lineage and schema evolution observable across the whole stack. The direct
modeling-to-analytics edge is the structural expression of requirement~R10 --- the
interface specified in \S\ref{subsec:ch3-contract}.

The components in layers~1--3 are standard for a Data Vault~2.0 deployment on a Lakehouse

\subsection{The Integration Contract}
\label{subsec:ch3-contract}

The integration contract is the centerpiece of the framework. Chapter~2 established that
Data Vault~2.0 and the Lakehouse are practiced together but their interface is specified by
neither paradigm (\S\ref{sec:ch2-tension}); this contract specifies it. It is a one-way
agreement: the agile modeling layer (provider) guarantees a set of properties on the
entities it exposes, and the native analytics layer (consumer) builds features only on
those guarantees. The construct borrows the data-contract pattern from current data
engineering practice \cite{jones2023datacontracts} \textit{(industry practice; not
peer-reviewed)} and binds it to Data Vault~2.0 semantics. Figure~\ref{fig:ch3-contract}
frames the interface.

Three mechanics make the clauses operational. \textit{Feature derivation:} features are
computed from Satellite attributes and Business Vault entities, never from raw staging,
and point-in-time joins key on \texttt{load\_dts} (G1, G4). \textit{Schema-evolution
propagation:} an additive change creates a new Satellite or column, the schema registry
issues a new compatible version, and feature pipelines opt into it explicitly; because no
attribute is mutated in place, a model trained on an earlier version keeps reading valid
inputs (G5). \textit{Format mediation:} the open table format stores each entity once and
serves join-based reconstruction for BI and columnar file scans for machine learning from
that single copy, so the two workloads never diverge into separate datasets \cite{deltalake2020,
armbrust2021} (G6).

\subsubsection*{Scope and stated assumptions}

The contract resolves part of the \S\ref{sec:ch2-tension} tension and scopes the rest
explicitly. Stating the limits is deliberate: an honest boundary is more defensible than
an overclaimed resolution.

\begin{itemize}[noitemsep, topsep=4pt]
  \item \textbf{A1 (single format).} The contract assumes one open table format across all
  layers. It does not address cross-format federation; mixing Delta and Iceberg is out of
  scope.
  \item \textbf{A2 (performance, conceded).} The contract does not eliminate the join-heavy
  cost of Vault reconstruction identified in \S\ref{sec:ch2-tension}; it confines it. The
  Business Vault and serving marts absorb the cost for BI, and feature pipelines that read
  the Raw Vault directly inherit it. This is a real limitation, not a solved problem.
  \item \textbf{A3 (history reconciliation).} Two history mechanisms coexist --- Satellite
  \texttt{load\_dts} and table-version time travel. The contract makes \texttt{load\_dts}
  the system of record for analytical point-in-time correctness; table versions are treated
  as operational metadata only. This removes the ambiguity flagged in
  Table~\ref{tab:align-conflict}.
  \item \textbf{A4 (interface only).} The contract governs the modeling-to-analytics
  interface. It does not specify model internals, serving latency, or BI tooling, which
  remain implementation choices.
\end{itemize}

\subsection{Design Rules and Invariants}
\label{subsec:ch3-invariants}

The contract is enforced by a small set of design invariants. Each is a property the
framework must hold at all times, stated so that it can be checked --- and contested ---
one at a time. The bracketed labels map each invariant to the requirement (R) or contract
clause (G) it enforces.

\begin{enumerate}[topsep=4pt, itemsep=2pt, leftmargin=2.4em]
  \item[\textbf{I1.}] Every analytical feature traces to a historized Satellite attribute; no feature originates outside the modeling layer. \hfill\textit{[R4, G1]}
  \item[\textbf{I2.}] The native analytics layer reads only from the modeling or serving layers, never from raw staging directly. \hfill\textit{[R10]}
  \item[\textbf{I3.}] Schema changes in the Raw Vault are additive --- new Satellites or columns; destructive changes are prohibited. \hfill\textit{[R2, G5]}
  \item[\textbf{I4.}] Business keys are stable and source-system-independent (hash keys). \hfill\textit{[R1, G2]}
  \item[\textbf{I5.}] Every entity entering the analytics layer carries a lineage stamp: source Satellite plus load timestamp. \hfill\textit{[R12, G3]}
  \item[\textbf{I6.}] Point-in-time correctness uses Satellite \texttt{load\_dts} as the temporal system of record, not table-version time travel. \hfill\textit{[A3]}
  \item[\textbf{I7.}] Business intelligence and machine learning read the same open-format tables; no parallel analytical copy is maintained. \hfill\textit{[R8, G6]}
  \item[\textbf{I8.}] Every deployed model is pinned to a feature-set schema version; an additive schema change cannot silently alter a deployed model's inputs. \hfill\textit{[R9, G5]}
\end{enumerate}

\noindent Invariants I1, I2, and I5 close the provenance of every analytical result back to
a governed source; I3, I6, and I8 are what let schema evolution and model training coexist
without breaking each other --- the property the literature reviewed in
\S\ref{sec:ch2-tension} leaves unspecified.

\section{Evaluation Methodology}
\label{sec:ch3-methodology}

The thesis builds no prototype, so each approach is judged against documented evidence
rather than measured performance. This is a stated limit, not a concealed one: the method
establishes \emph{relative} standing among approaches under a fixed rubric, not absolute
metrics. Defining the method before applying it is what separates the comparison in
\S\ref{sec:ch3-comparison} from an opinion table. Figure~\ref{fig:ch3-protocol} shows the

\textbf{Instrument and scoring.} The instrument is construct~C2 reused without change: the
six criteria of Table~\ref{tab:c2-grid} and the three-level rubric of
Table~\ref{tab:c2-rubric}. Reusing it unchanged is deliberate --- the proposed framework is
judged by the same yardstick Chapter~2 applied to the existing approaches, so the
comparison cannot be accused of moving the goalposts. Each criterion is scored on an
ordinal scale --- Low, Medium, High --- whose meaning is fixed \emph{per criterion} by the
rubric. High is the favourable pole for every criterion, including implementation
complexity, where High denotes low burden rather than high effort.

\textbf{Evidence rule.} No bare score enters the matrix. Every rating carries a
justification: a cited source, or an explicit argument from the framework's stated
definition and invariants. Evidence is tiered. Peer-reviewed sources carry primary weight;
industry and vendor sources are admitted only where peer-reviewed evidence is absent --- as
it largely is for the Data Vault~2.0--Lakehouse composition --- and are flagged in-text as
not peer-reviewed. A rating that rests only on vendor evidence is treated as weaker than one
grounded in peer-reviewed work, and the discussion (\S\ref{sec:ch3-discussion}) revisits the
ratings most exposed to this gap.

\textbf{Structural criteria (1, 3).} The classical paradigms score Low on both structural
flexibility and schema evolution. Kimball's conformed dimensions and Inmon's normalized
core each turn a new source or a structural change into a redesign event
\cite{kimball2013, inmon2005}. Data Vault~2.0 and the proposed framework score High on both:
the Hub--Link--Satellite decomposition absorbs new sources and structural change additively
\cite{linstedt2015}. The proposed framework inherits this directly, and its schema registry
(invariant~I3) hardens Data Vault~2.0's additive convention into an enforced compatibility
guarantee.

\textbf{Query performance (2).} Performance inverts the ranking. Kimball scores High ---
the star schema is built for fast interactive queries \cite{kimball2013}. Data Vault~2.0
scores Low: business views are reconstructed through hub--link--satellite joins, the
workload columnar file scans handle worst (\S\ref{sec:ch2-tension}). Inmon and the proposed
framework sit at Medium; both interpose a serving layer --- Inmon's data marts, the
framework's Gold marts and Business Vault PIT/Bridge structures --- that absorbs the join
cost for BI without removing it. The framework does not claim Kimball's performance;
assumption~A2 concedes the residual cost explicitly.

\textbf{Implementation complexity (4).} This is where the proposed framework is weakest, and
the matrix says so. Inmon's enterprise normalized core, Data Vault~2.0's modeling rigor and
specialized skills, and the proposed framework all score Low --- high burden. The framework
is arguably the most demanding of the four: it carries Data Vault~2.0's full modeling cost
and adds a native analytics layer, a governance plane, and the integration contract. Kimball
scores Medium, reflecting its comparatively faster delivery of business intelligence
\cite{kimball2013}. A framework that scored High here would not be credible.

\textbf{Analytical capability (5).} Only the proposed framework reaches High. Kimball,
Inmon, and Data Vault~2.0 are descriptive-to-diagnostic by construction and score Low; none
integrates predictive or prescriptive capability natively, as Chapter~2 established
\cite{kimball2013, inmon2005, linstedt2015}. The framework's native analytics layer, reading
feature-ready entities across the integration contract, lifts it to prescriptive reach with
models as first-class pipeline citizens \cite{armbrust2021, kreuzberger2023}.

\textbf{Composability with modern storage (6).} Composability separates the framework from
its parent. Data Vault~2.0 scores Medium: it runs on the Lakehouse, but by workaround ---
vendor practice places the vault on Delta storage and absorbs the join cost downstream
\cite{databricks2022, moronta2026} \textit{(industry practice; not peer-reviewed)}, with a
peer-reviewed account confirming the pattern for data lakes \cite{giebler2019dv}. Inmon
scores Low and Kimball Medium; neither was designed for file-based storage. The proposed
framework scores High because composition is designed in rather than retrofitted: a single
open table format and the integration contract make the modeling and analytics layers share
one physical copy (invariant~I7). This is the rating most exposed to the evidence gap of
\S\ref{sec:ch2-tension}, and \S\ref{sec:ch3-discussion} returns to it.

Read across, the matrix has a clear shape. The proposed framework leads on the structural,
analytical, and composability criteria, matches the field on query performance, and pays
for this on implementation complexity. That trade-off --- capability bought with build cost
--- is the subject of the discussion that follows.

\section{Discussion}
\label{sec:ch3-discussion}

\textbf{The trade-off the framework makes.} The matrix of \S\ref{sec:ch3-comparison} shows
a single coherent bargain rather than a uniform advantage. The framework buys structural
agility, native analytical capability, and clean composability, and it pays in
implementation complexity and a query-performance ceiling below Kimball's. The trade is
deliberate. Structural and analytical scalability are the two axes the introduction set out
to satisfy jointly (RQ1, RQ2); query performance is recoverable at the serving layer, and
implementation complexity is a one-time build cost. An organization that needs neither axis
should not pay that cost --- which is the question of applicability.

\textbf{When the framework is worth its cost.} Figure~\ref{fig:ch3-applicability} maps the
decision against two factors. The framework is justified only in the top-right quadrant:
high source heterogeneity and change rate, combined with ambition beyond descriptive
reporting. There, both scalability axes are exercised and the build cost is repaid. In the
bottom-left quadrant --- stable sources, descriptive reporting --- a Kimball dimensional
warehouse is sufficient and far cheaper, and the framework is overkill \cite{kimball2013}.
The two off-diagonal quadrants are partial: with stable sources but predictive ambition, the
Vault's structural agility is underused; with high churn but no analytical ambition, Data
Vault~2.0 alone meets the need without the analytics layer \cite{linstedt2015}. The
framework does not claim universal applicability, and that boundary is part of the
contribution.

\textbf{Threats to validity, revisited.} The threats stated in
Table~\ref{tab:ch3-threats} bear unevenly on the results. The structural and analytical
ratings rest on foundational, peer-reviewed sources and are the most secure. The
composability rating (criterion~6) is the most exposed: it is the one most dependent on
industry and vendor evidence (threat~T3) and on a literature that does not yet evaluate the
composition formally (threat~T2). The self-assessment threat (T4) is contained by the
matrix itself, which the framework does not sweep. None of these threats is dissolved here;
they qualify the strength of the claims rather than the claims themselves.

\textbf{Limitations.} Three limits follow directly and are stated plainly.

\begin{itemize}[noitemsep, topsep=4pt]
  \item \textbf{No empirical validation.} The framework is evaluated conceptually, not
  measured. Its ratings predict relative standing; they are not benchmarks. Empirical
  validation is the principal direction for future work.
  \item \textbf{Composability evidence is thin.} The central composability claim leans on
  vendor practice and a small peer-reviewed base \cite{databricks2022, giebler2019dv}. Until
  the composition is studied empirically, that claim is scoped, not settled.
  \item \textbf{Reference design, not an implementation.} The framework specifies layers, a
  contract, and invariants; it deliberately leaves engine choice, serving latency, and
  tooling open (assumption~A4). It is a blueprint to instantiate, not a system to deploy
  as-is.
\end{itemize}

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}

This chapter delivered construct~C3. It specified a layered reference framework as a formal
artifact, not a block diagram: four functional layers on a shared open-format substrate,
component definitions with stated inputs and outputs, an integration contract of six
clauses between the agile modeling layer and the native analytics layer, and eight design
invariants that make the contract checkable. It then evaluated the framework with the C2
instrument under a stated method, conceding where the framework is weak --- query
performance and implementation complexity --- rather than claiming a clean sweep.
